# Triton 4 + TritOS Desktop 2.0: storage units, TritFS v2, real time, and the app shelf

ConsciousNode SoftWorks, MIT. Xinu rules: single-file pages, zero dependencies, offline. **Inline everything, and label every inline** (provenance comments plus `LIFTS.md`).

Triton is a balanced-ternary computer. Triton 3 was specced as an emulator. Its storage is one fixed disk of 2,187 sectors, and TritOS Desktop's directory holds 44 files, flat and append-only. We are now designing real hardware for it (a card computer), so the machine grows up: **Triton 4**. The emulator remains the answer key the hardware will be checked against, so it must be exact.

## Part A: the Triton 4 machine (`triton4.html`, both `TritonJS` and `TritonWASM`)

Build it from `triton3.html`'s machine. Leave `triton3.html` itself unchanged.

1. **Ports 28–32, vector 12**, exactly as in `TRITON-4-STORAGE-TIME.md`:
   - `DISK_UNIT`, `DISK_SIZE` and `DISK_FLAGS` (the changed bit clears on read);
   - `TIMER_MODE`, `RTC_SECONDS`;
   - `IRQ_MEDIA` (IRQ bit 5 = 32);
   - `DISK_ERR` 4 = bad or empty unit.
   
   All existing disk ports (7–8, 17–21) act on the selected unit. Its LBA range is `0 .. DISK_SIZE−1`, and port 7's stream address wraps at that unit's size × 729.
2. **Compatibility:**
   - reset selects unit 0 and timer mode 0;
   - unit 0 is always 2,187 sectors with the legacy layout;
   - **in T2 mode, ports 28+ behave as in Triton 3** (read 0, writes ignored);
   - a program that never touches ports 28+ must run **step-for-step identically** to Triton 3.1.1.
3. **Units are sparse** (store only non-zero sectors), so a 3^13-sector unit costs nothing until written.
   - Default machine: unit 0 (legacy, 2,187), and unit 1, the home disk, **3^10 = 59,049 sectors**, blank.
   - Unit 2 is the cartridge slot (removable). Units 3–26 are removable images.
   - `TritonWASM` may reach units through host imports (it's a device), but the two VMs must stay bit-identical.
4. **Timer mode 1:** `TIMER_TICKS` and the periodic timer count real time at 200 kHz (one tick per 5 µs) from a host clock.
   - The clock is a **documented, injectable device input**, so tests can drive it.
   - Mode 0 is unchanged.
5. **RTC:** seconds since 2000-01-01 00:00 UTC from the same injectable clock. Writing it sets an offset.
6. **Units panel in the page:**
   - per unit: present, size, label (if TritFS), write-protect toggle;
   - insert (file picker and drag-drop of `.tdisk` or raw), eject (raises `IRQ_MEDIA`), export;
   - new blank unit of 3^7 / 3^10 / 3^13 sectors.
   
   The self-contained HTML snapshot export must carry all units (sparse). The unit 0 raw export stays byte-identical to Triton 3's `exportDiskImage`.
7. **Fault injector (device API, test use):** "cut power after the next N sector writes". The machine halts as if unplugged. Unit contents persist, and RAM does not.
8. **`ISA-4.md`**, generated by script from `triton4.html` the way `ISA-3.md` is.

## Part B: TritOS Desktop 2.0 (`desktop/tritos-desktop-2.html` on the Triton 4 machine)

1. **TritFS v2 in guest assembly**, exactly per `TRITFS-V2.md`. In particular:
   - copy-on-write updates, with the superblock write as the commit;
   - old chains freed only after the commit;
   - fsck that reports problems and repairs only orphans.
   
   Put it in a labeled driver (`fs` v2) in `DRIVERS.md`. Units larger than the link-table cache must page the table, not load it whole.
2. **Mounting:**
   - unit 0 shows as `0:/` (legacy, read and write in its old format);
   - every present TritFS unit shows as `U:/`;
   - a blank home disk is formatted `HOME` on first boot;
   - media change (`IRQ_MEDIA`) mounts and unmounts removable units without a reboot;
   - a unit removed mid-operation makes that operation fail cleanly. Nothing else is harmed.
3. **Path syscalls**, documented in `DESKTOP.md`:
   - list, stat, read, write, mkdir, delete, rename, copy;
   - unit info: size, free, label;
   - format, fsck.
   
   **The old `SYS_FS_*` calls keep working on unit 0**, so 1.1.2-era apps still run.
4. **Files app:**
   - browse units and folders;
   - new folder, rename, delete (with confirm), copy and move across units;
   - info (type, size, modified time);
   - **"Copy legacy files"**: `0:/*` → `1:/legacy/`.
5. **Disks app:** units, labels, free space, format, check (fsck), eject.
6. **The bundled apps save to the home disk** (`1:/docs/…` etc.), falling back to unit 0 when there is no home disk.
7. **App shelf:**
   - the launcher lists every folder in `1:/apps` and `2:/apps` (the cartridge), showing its `icon` (image file) when present;
   - launching reads `main` (an executable in the format `SYS_EXEC_BUF` accepts; document that format) and runs it as a user task;
   - installing a cartridge app = copying its folder to `1:/apps`.
8. **Time:** the kernel switches to timer mode 1 at boot. `SYS_GET_MS` and every timed app run on real time. The Clock app and file modified times come from the RTC.
9. Version strings say `TritOS Desktop 2.0`, defined once.

## Forbidden

- Calling `tritfs-ref.js` from the guest or the host, or a host-side file system. Disk access goes through the disk ports only.
- Host code reading or writing guest memory beyond the existing documented debug panel reads. No test detection.
- Precomputed disk images in the page, except a blank unit and the TritOS boot image built by the build script.
- **Verbatim:** "If a requirement can't be met, or conflicts with another, say so in REPORT.md and leave it failing. Never change emulator or VM accessors, I/O, consoles, test harnesses, or the auditor's scripts to make a check pass. An emulator must never read or write a guest's private memory."
- Do not predict, rank or praise results anywhere in code, docs or UI.

## Tests

Tests go in `tests/` (machine) and `desktop/tests/` (OS), with run-all scripts. The harness may only:
- push keys and mouse events through the device methods;
- insert, eject and export units through the units API;
- drive the injectable clock;
- read the framebuffer, unit images and the documented debug panel.

1. **Machine compatibility:**
   - the full Triton 3 test suite passes on `triton4.html`;
   - a differential runs Triton 3.1.1 and Triton 4 on the same programs (every existing T3 test program, plus 50 seeded random programs that avoid ports 28+) and compares state hashes **at every step**;
   - **positive control:** a program that reads port 29 must diverge.
2. **JS ↔ WASM:** both VMs agree step for step on the unit, timer-mode and RTC test programs.
3. **Ports:**
   - each port's read/write semantics;
   - bad unit → `DISK_ERR` 4;
   - DMA past a unit's end → bad sector;
   - `IRQ_MEDIA` on insert and eject;
   - the changed flag clears on read;
   - T2 mode sees none of it.
4. **Timer mode 1:** with the clock driven 1,000 ms forward and the CPU run for 10,000 or 1,000,000 steps, `TIMER_TICKS` advances by 200,000 both times. In mode 0 it follows steps.
5. **TritFS conformance, with the reference as oracle:**
   - **guest → ref:** the guest does a seeded script of 500 operations (mkdir, write, overwrite, rename, delete, copy across units), then the exported unit is opened with `tritfs-ref.js`: the same tree, tryte-identical file data, and `fsck` with zero problems and zero orphans;
   - **ref → guest:** an image built by the reference is read by the guest, which matches every file;
   - 3 seeds each.
6. **Scale:**
   - 1,000 files in one folder, and 10 levels of folders;
   - a 3^13-sector unit with files written past sector 1,000,000 (link-table paging);
   - after deleting everything, free space returns exactly to the post-format value.
7. **Power cut:**
   - for each of 5 operations (write, overwrite, delete, mkdir, rename), interrupt the guest after each sector write in turn: cut it with the fault injector, reboot, then remount;
   - the reference `fsck` finds no problems, and the tree equals the before- or after-state;
   - report how many cut points were tested.
8. **Positive controls:**
   - the guest fsck finds a planted cross-link, a loop and an orphan (orphan repaired, the others reported);
   - an image with a corrupted superblock magic is refused, not mounted.
9. **Media:**
   - insert a cartridge image built by the reference holding `/apps/<test>/main` and `icon`: it appears in the launcher without a reboot, launches, and draws its expected pixels;
   - eject during a copy: the copy fails cleanly and the home disk passes `fsck`.
10. **Legacy:**
    - TritOS Desktop 1.1.2's guest image, unchanged, boots on Triton 4 and its 40-test suite passes;
    - in 2.0, "Copy legacy files" copies every `0:/` file tryte-identical.
11. **No regressions:** every 1.1.2 desktop test that still applies passes on 2.0; list any test retired and why.
